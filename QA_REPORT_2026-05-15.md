## HEADLINE

The core monetization engine is **solid** — wallet, paid messages, first-3-free, subscriptions, free-message enforcement, unlockables, and the 25/75 fee split all work **correctly and exactly for a brand-new creator + brand-new customer**. Wallet ledger reconciled to the cent across an 8-step session.

**But the platform cannot onboard a single new creator.** The creator-application → admin-approval pipeline is broken end-to-end (Launch Blocker #1). Every existing creator only has the role because it was granted by direct DB edits. This is a hard launch blocker and is the #1 priority.

Separately, the prior QA process never actually tested onboarding the real way — it bypassed both gates (email confirm + approval) with manual `UPDATE` statements — so PROJECT_STATE's "onboarding works from zero state" was an untested assumption. It does not.

## LAUNCH BLOCKERS

### 🔴 LB#1 — Creator approval pipeline is completely broken; no new creator can be onboarded

**Summary:** A fresh creator signs up, submits the application, sees "Application Submitted!" then "Application Under Review" — but the application never reaches the admin. The `/admin` panel shows "No applications yet"; the creator is absent from the user list and search. No new creator can ever be approved through the product.

**Reproduction:**
1. Sign up a fresh creator via `/creator-auth` → Apply (2-step form). Submit.
2. "Application Submitted!" screen appears.
3. Sign in as that creator → lands on `/creator-application-pending` "Application Under Review".
4. Sign in as admin → `/admin` → Applications tab.

**Expected:** the new application is listed and approvable.
**Actual:** "No applications yet"; creator not in All-users list or search.

**Suspected root cause — three compounding defects:**
- **DEFECT B (decisive) — invalid SQL.** `supabase/migrations/20260512000006_creator_application_fields.sql` uses `CREATE POLICY IF NOT EXISTS "Admins can manage creator verifications" …`. `CREATE POLICY` has **no `IF NOT EXISTS` clause in PostgreSQL** — that statement is a syntax error, so the admin RLS policy was never created in prod. The only SELECT policy on `creator_verifications` is `"Creators can view own verification" USING (auth.uid() = creator_id)`, so the admin's query (`AdminDashboard.tsx` line 117) can never return other users' rows.
- **DEFECT A — swallowed write error.** `CreatorAuth.tsx` → `submitApplication()` does `await supabase.from('creator_verifications').upsert(...)` and never checks the returned `{ error }`. If the write fails (e.g. FK race: `creator_id NOT NULL REFERENCES profiles(id)` vs. the `handle_new_user` trigger that creates the profile — the code comment says to add a delay but the `authData.session` branch doesn't), `setSignupSuccess(true)` still runs → false "Application Submitted!".
- **DEFECT C — false reassurance.** `CreatorAuth.tsx` → `handleSignIn`: the `else` ("No application yet") branch *also* navigates to `/creator-application-pending`, so a creator with no verification row still sees "Application Under Review".

**Affected files:** `supabase/migrations/20260512000006_creator_application_fields.sql` (RLS/schema); `src/pages/CreatorAuth.tsx` (frontend); `src/pages/AdminDashboard.tsx` (query is correct, starved by missing policy).

**Classification:** RLS + schema + frontend. **Platform-wide** (every new creator).

**Recommended fix direction:**
1. Replace `CREATE POLICY IF NOT EXISTS …` with `DROP POLICY IF EXISTS … ; CREATE POLICY …` in a new tracked migration. Verify in `pg_policies` that the admin policy actually exists in prod.
2. In `submitApplication()`, destructure `{ error }` from the upsert and throw on it so failures surface as a real toast. Ensure the `profiles` row exists before inserting `creator_verifications` (await/retry, or move signup→profile→verification into one SECURITY DEFINER RPC).
3. In `handleSignIn`, the no-verification-row branch must NOT show "Application Under Review" — send the user back to Apply or show a real error.
4. After fix: confirm a fresh creator's application appears in `/admin` and is approvable end-to-end with zero DB hand-edits.

## HIGH / MEDIUM ISSUES (not launch blockers, but fix before or shortly after launch)

### 🟠 AUDIT-1 (HIGH) — Creator settings pages report false success & silently lose data when no `creator_settings` row exists
- **Confirmed in browser.** On a fresh creator with no `creator_settings` row: `/settings/messaging` shows hardcoded defaults; changing a value + Save → toast "Settings saved successfully" → reload → value reverted. The save did nothing.
- **Root cause:** `MessagingSettings.tsx` / `SocialsSettings.tsx` fetch with `.single()` (throws on 0 rows, caught + swallowed) and save with `.update(...).eq('user_id', …)` — on a non-existent row this updates 0 rows, returns no error, and the success toast fires regardless.
- **Realistic** because there's no auto-routing to CreatorOnboarding after approval (ONBOARDING-3) — a creator can reach settings before the row exists.
- **Affected:** `src/pages/settings/MessagingSettings.tsx`, `src/pages/settings/SocialsSettings.tsx`. Frontend. Platform-wide.
- **Fix direction:** use `.upsert(... onConflict: 'user_id')` (like `CreatorOnboarding` and `SubscriptionTiersManager` already do); check `.update()` affected-row count and surface a real error otherwise.

### 🟠 ONBOARDING-3 (MEDIUM) — no automatic routing to CreatorOnboarding after a creator gets the role
- A newly-roled creator lands on `/dashboard`; nothing routes them through `CreatorOnboarding`, so `creator_settings`/`message_packs` may never be created → triggers AUDIT-1 and leaves `price_per_message` at the $5 RPC default.
- **Fix direction:** route to `/creator-onboarding` until `creator_settings` exists, or create the row at approval time.

### 🟡 ROUTING-1 (MEDIUM) — `/:id` catch-all swallows unknown paths as "Creator not found"
- `App.tsx` has `<Route path="/:id" element={<CreatorProfile />} />` matching any single-segment path. `/admin-dashboard` (and any typo'd/stale URL) → "Creator not found" toast → bounce home, instead of a clean 404.
- **Real impact this session:** PROJECT_STATE.md documents the admin route as `/admin-dashboard`; the actual route is `/admin`. Following the doc URL gave a confusing error and blocked the user from reaching the admin panel.
- **Fix direction:** reserve known top-level paths or prefix creator profiles (e.g. `/u/:id`); validate the id before showing the not-found creator error. **Also correct PROJECT_STATE.md to `/admin`.**

### 🟡 CHAT-UX-1 (MEDIUM) — payment-option card never collapses for non-subscribed customers
- For a non-subscribed pay-per-message customer, the "Choose a payment option to start chatting" block stays pinned at the top of the chat even after the conversation is active, pushing real messages below the fold. (For subscribed customers it correctly collapses.)
- **Affected:** `MessagingInterface.tsx`. Fix direction: collapse the card once a conversation has messages and the customer has balance.
