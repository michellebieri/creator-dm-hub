## RESIDUAL DEFECT — LB#4b: Double PKCE Exchange in AuthCallback.tsx

**Severity:** HIGH — same user-facing failure as pre-fix. Happy path broken for all creator signups.

**Root cause (identified from source + evidence):**

`client.ts` has `detectSessionInUrl: true`. This makes the Supabase auth-js client **automatically** call `exchangeCodeForSession(code)` when it initialises on any page that has `?code=` in the URL — including `/auth/callback?code=XXXX&intent=creator`.

Sequence of events when the browser lands on `/auth/callback?code=XXXX`:

1. auth-js client initialises → detects `?code=` in URL via `detectSessionInUrl` → **auto-calls `exchangeCodeForSession(code)` internally** → succeeds → writes `sb-*-auth-token` to localStorage → **deletes `sb-*-auth-token-code-verifier`** (expected cleanup)
2. `AuthCallback.tsx` `useEffect` runs → reads `code` from `useSearchParams()` → **explicitly calls `supabase.auth.exchangeCodeForSession(code)` at line 53**
3. auth-js tries to read `code_verifier` from localStorage → it's already been deleted by step 1 → sends empty `code_verifier` to Supabase server
4. Supabase server returns: `"invalid request: both auth code and code verifier should be non-empty"`
5. `AuthCallback.tsx` error handler at line 56 navigates to `/creator-auth#error=access_denied&error_code=exchange_failed&...`
6. `CreatorAuth.tsx` detects the `#error=` fragment → renders `AuthErrorBanner`

The proof: `sb-jhzcmdsaajvftjbhdunt-auth-token` IS in localStorage (step 1 succeeded), `email_confirmed_at` IS set (2026-05-17T10:53:43.113513Z), but the error banner shows (step 4 failure from step 2's call).

**Affected file:** `src/pages/AuthCallback.tsx` line 53 — `const { data, error } = await supabase.auth.exchangeCodeForSession(code);`

**Fix options for Claude Code (in order of preference):**

**Option A — Recommended (one-line change in `client.ts`):**
Set `detectSessionInUrl: false` in `createClient` auth options. This disables the auto-exchange, leaving `AuthCallback.tsx`'s explicit call as the only exchange. The explicit call succeeds because the `code_verifier` is still in localStorage.

```typescript
// client.ts
auth: {
  persistSession: true,
  autoRefreshToken: true,
  flowType: 'pkce',
  detectSessionInUrl: false,  // ← change: prevent auto-exchange racing with AuthCallback
}
```

**Option B — Change in `AuthCallback.tsx`:**
Before calling `exchangeCodeForSession`, check for an existing valid session (from the auto-exchange). If a session already exists, skip the exchange and proceed to routing:

```typescript
// AuthCallback.tsx — replace the exchangeCodeForSession block:
const { data: sessionData } = await supabase.auth.getSession();
let session = sessionData?.session;
if (!session) {
  const { data, error } = await supabase.auth.exchangeCodeForSession(code);
  if (error || !data?.session) { /* error routing */ }
  session = data.session;
}
// proceed with session...
```

**Option C (not recommended):** Remove `exchangeCodeForSession` from `AuthCallback.tsx` entirely and rely solely on `detectSessionInUrl` auto-exchange, then call `getSession()` to retrieve the session. Higher risk — less explicit control over timing.

## WHAT IS FIXED (commit `9f69320`)

1. **Storage bypass defect** — Removing `storage: localStorage` from `createClient` options means auth-js now uses `supportsLocalStorage()` to validate the storage adapter before writing. The write no longer silently fails in Vite/Vercel environments where the raw global may behave differently.

2. **Race condition defect** — `await supabase.auth.signOut()` before every `signUp()` clears any existing session, terminating the auto-refresh ticker. No concurrent `_removeSession()` can race with the `code_verifier` write during the async signUp HTTP gap. **This is confirmed working** — the `code_verifier` IS present after signup (Step 3 PASS).

## WHAT IS NOT FIXED (new residual defect)

3. **Double PKCE exchange** — `detectSessionInUrl: true` auto-exchanges the code when `AuthCallback` loads; the explicit `exchangeCodeForSession(code)` in the same component then fails because the `code_verifier` is already consumed. One targeted fix (Option A above) should close this.
